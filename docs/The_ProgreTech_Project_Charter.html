Authoritative direction

North star: autonomous delivery that becomes less dependent on outside AI over time

ProgreTech is building an AI-operated software, PWA and automation factory. Edwin supplies intent, business authority, protected-environment bridging and consequential approvals. Rend, Mak and Lyra progressively convert that intent into specifications, code, tests, deployable artifacts, operating evidence, training material and follow-on improvements.

Primary maturity rule: outside intelligence is a teacher, not the workforce. The factory attempts work locally, recalls validated knowledge, escalates only when needed, validates the lesson, retains what was learned and retries locally when practical.

Hardware, models, plugins, memory systems and orchestration frameworks are supporting infrastructure. They are justified only when they measurably improve safe autonomous task success, learning, recovery, throughput or delivery quality.

Qualification is evidence-driven, not parameter-count driven

MeasureWhat matters
Autonomous completionCan the model finish representative ProgreTech work with the required evidence and without excessive retries?
Tool-use reliabilityDoes it invoke tools correctly, preserve task state, respect boundaries and complete agentic loops?
Recovery qualityCan it use durable state, classify failures and resume without replaying completed actions?
Latency / throughputIs iteration fast enough for practical autonomous work, including concurrent agents?
Context / memory behaviorCan it use the context actually required without destabilizing the worker loop or exhausting local memory?
Resource efficiencyRAM use, concurrency headroom and power per useful deliverable remain within the always-on operating goal.
Teacher escalationDoes the model reduce repeated external-teacher calls on known problem classes?

Do not prematurely hard-code a permanent “best” model. Candidate families and quantizations are qualified against the same factory workload. A smaller high-quality model may beat a larger quantized model when tool reliability, latency and concurrency are considered; a larger local senior is justified only where it improves difficult-task completion enough to offset its resource cost.

Migration doctrine retained

The MS-S1 MAX migration established a whole-system migration rule, not a MemPalace-only copy. The durable ProgreTech identity to preserve across any future host move includes Git repositories/history, MemPalace, executable catalog and knowledge ledgers, task/recovery evidence, policies, configuration, validated skills, OpenClaw/Telegram integration configuration and support-storage structure. Secrets remain handled separately under existing policy.

Clean-host rule: future migrations should not blindly clone a prior home directory or operating-system debris. Build a clean host, restore the durable ProgreTech identity, re-run representative acceptance, and retain the prior host as rollback/reference until the new host is formally accepted.

Durable learning substrate

MemPalace is the durable learning layer — not a side roadmap

PT-2026-009 proved the agent-neutral MemPalace foundation: SQLite/FTS5, explicit recall/learn, private/shared/project/procedure scopes, provenance, duplicate protection, correction/supersession, admission controls and migration-safe backup. It is part of the factory substrate rather than a separate future project.

Teacher-derived lessons, validated fixes, reusable implementation patterns and failure signatures should be admitted deliberately into the appropriate project/procedure/shared scope. Current Git, tests and configuration remain higher authority than remembered history.

MemPalace stores

Decisions, rationale, reusable troubleshooting knowledge, validated procedures, project context, handoffs, learned patterns, provenance, confidence and supersession history.

It does not replace

Git for code, the task ledger for task state, artifacts for evidence, or human approval for authority. Raw chat transcripts, secrets and transient execution state do not become memory by default.

Team model

Rend keeps orchestration/SRE memory; Mak receives implementation/engineering memory; Lyra receives product/front-office memory. Shared memory contains curated project facts, conventions, reusable factory knowledge and attributable handoffs. Lyra and Mak inherit the same schema rather than spawning new memory architectures.

Factory product boundary

The service catalog defines what the autonomous factory is learning to deliver

The service catalog is not a parallel business roadmap. It is the acceptance envelope for the same factory roadmap. A capability enters the catalog only after ProgreTech has a known implementation pattern, security boundary, test strategy and maintainable delivery path.

Create the first self-contained HTML journal from the original autonomous-intern concept through Rend's current commissioned state. Preserve the real evolution of the architecture, hardware, operating model, interfaces, safety boundaries, milestones, failed approaches and design changes.

Preserved Autonomous OS roadmap

Autonomous Presence: voice + bounded visual perception + living heartbeat

The presence roadmap remains one coherent layer rather than a collection of disconnected UI experiments. The accepted voice path, camera as bounded local visual perception, runtime state and Ubuntu desktop should converge into a lightweight Autonomous Presence surface for Rend and later Lyra/Mak.

Idle / available

Calm, low-motion presence with a subtle heartbeat/glow and minimal resource use.

Listening

Clearly visible listening state when human-input capture is explicitly active.

Speaking

Visual pulse, halo or waveform may follow synthesized-audio amplitude so the desktop visibly responds to Rend's speech.

Processing / working

State must come from actual runtime events rather than decorative timers.

Recovery / attention

Distinct state when intervention, recovery or a blocked workflow needs attention.

Multi-agent / multi-model

Show when Rend is assisting Lyra/Mak, coordinating work or using multiple local capabilities without requiring a terminal.

Bounded visual perception

The camera is treated as a local, explicit capability — effectively Rend's eyes — rather than a permanent surveillance feed. A later presence layer may combine listening and perception, follow ordinary movement around the active workstation area, and support natural interaction with whoever is in front of the computer.

Privacy boundary: perception must be explicit, locally bounded and observable. It must not imply unrestricted recording, silent background surveillance, biometric identification or automatic persistent retention. Persistent capture/retention requires a separately approved purpose and policy, and the presence surface must make microphone/camera activation obvious.

Hardware mutability

Microphones, speakers and cameras are capabilities, not hard-coded device identities. Rend should discover active PipeWire/Pulse routes and camera capabilities at runtime, allow bounded explicit overrides, and survive hardware replacement without application-code edits.

Office Chatter

Office Chatter remains an optional, bounded social-presence layer. During configured office hours, Rend may occasionally make a short contextual remark related to work he is actually doing, a locally observed non-sensitive event, or conversational context heard while listening is explicitly active. When Lyra/Mak join, the same mechanism may support occasional lightweight agent-to-agent conversation about current work, handoffs or discoveries.

Chatter discipline: opt-in, schedule-aware, immediately yields to active work or STOP, stays quiet outside configured mode, does not manufacture activity just to appear alive, and does not automatically turn ephemeral camera/audio context into durable memory.

Engineering constraints

  • Local, lightweight and non-blocking; agent workloads win resource contention.
  • Fail safely to a static/quiet presence if the animation service stops.
  • Presence states should mirror factual runtime events, not simulated activity.
  • The same framework should later support Lyra and Mak with distinct visual identities while preserving their separate authority and task state.
Roadmap position: presence is preserved and may receive bounded maintenance, but major new presentation work should not displace the active model/capability/commissioning/factory-proof gates. The already-qualified voice and Office Chatter foundations remain usable now; richer wallpaper/camera integration can continue when it does not threaten the primary factory sequence.
Non-negotiable operating rules

Authority, safety and evidence remain stable while capability grows

Edwin remains owner

Consequential commitments, production/release authority, spending and protected-environment actions remain governed by explicit approval/runbooks.

STOP / CANCEL wins

Cancellation outranks queued actions, retries, recovery, heartbeat work, teacher guidance and prior authorization. Resumed execution must re-read durable cancellation state before consequential action.

External systems boundary

Agents may work from artifacts deliberately provided for the task. Access to employer or client systems, credentials, organization repositories, and authentication requires explicit task authorization.

Git is implementation truth

Unrelated dirty state is preserved or work stops. Local closure and remote publication are distinct states with explicit provenance.

Evidence before promotion

A model, plugin, skill or factory capability becomes “working” only after demonstrated behavior and acceptance evidence. Installation/configuration alone is not proof.

External AI stays advisory

External providers may teach, critique or clarify bounded gaps. They do not become default workers, expand authority or bypass local validation and durable state.
